# Т06: Telegram и контроль сроков

Telegram доставляет уведомления; действия с нарядом выполняются в PWA после обычного входа. Привязка Telegram не создаёт сессию приложения. Токены, webhook secret, chat_id и личные данные не сохраняются в Git или отчётах.

## Настройка бота

1. Открыть официальный [BotFather](https://t.me/BotFather), выполнить /newbot и сохранить выданный токен локально.
2. Скопировать .env.example в .env в корне репозитория. Заполнить TELEGRAM_BOT_TOKEN, TELEGRAM_BOT_USERNAME (без @), TELEGRAM_WEBHOOK_SECRET и PUBLIC_BASE_URL. Адрес приложения должен быть публичным HTTPS; localhost для webhook не подходит. SESSION_COOKIE_SECURE=true для HTTPS.
3. Создать отдельный webhook secret командой из services/api:

       uv run python -c "import secrets; print(secrets.token_urlsafe(32))"

   Результат сохранить только в .env. Это отдельное значение от токена бота.
4. Выполнить миграции до запуска API/worker: `uv run alembic upgrade head`. Для Compose DATABASE_URL использует хост db, для локального запуска — localhost. Учётные записи создаются существующей процедурой проекта; Telegram их не создаёт.
5. Запустить приложение и worker: `docker compose up --build -d`. Worker использует тот же API-образ и PostgreSQL, ждёт успешных миграций. Для локального запуска из services/api отдельными процессами: `uv run uvicorn app.main:app` и `uv run python -m app.workers.main`.
6. Явно зарегистрировать webhook командой `uv run python -m app.modules.telegram.manage set-webhook`; проверить `uv run python -m app.modules.telegram.manage info`. Команды запускаются из services/api с локальным .env. При старте приложения webhook не регистрируется автоматически. Не передавать токен в URL командной строки или историю терминала.

Официальный [Bot API](https://core.telegram.org/bots/api#setwebhook) описывает HTTPS webhook и заголовок X-Telegram-Bot-Api-Secret-Token; [deep linking](https://core.telegram.org/bots/features#deep-linking) — передачу одноразового параметра start. Reverse proxy должен пропускать POST /api/v1/telegram/webhook и этот заголовок. Не записывать body webhook и содержимое ответов link-token в access/debug logs.

## Привязка сотрудника

Вошедший сотрудник вызывает POST /api/v1/telegram/link-token с обычными cookie, Origin и X-CSRF-Token приложения. Ответ содержит token, url и expires_at. Поле url — ссылка в личный чат бота с одноразовым параметром start; срок — 10 минут. В БД хранится только хеш токена. Открыть ссылку и нажать «Старт» в Telegram, затем проверить GET /api/v1/telegram/status. Общий чат не используется для привязки.

GET /api/v1/telegram/status показывает подключение без Telegram ID. POST /api/v1/telegram/unlink требует входа и CSRF; после отключения старые токены не восстанавливают привязку. Один Telegram-аккаунт не привязывается одновременно к разным сотрудникам. Telegram-ссылка не заменяет авторизацию в PWA.

## Передача фронтенду Т04

Панель подключения использует новые маршруты через типизированные OpenAPI-контракты. Telegram-кнопка «Открыть наряд» ведёт на /work-orders/{uuid} в PWA; при отсутствии сессии нужен обычный вход с возвращением на эту карточку. GET-ссылка не принимает и не закрывает работу. В текущей main ещё нет экрана карточки Т04; переход на двух телефонах остаётся живой проверкой после его реализации.

Статусы доставки доступны через GET /api/v1/work-orders/{id}/notifications только пользователям с доступом к наряду. Ответ не содержит токенов, Telegram chat_id и сырых внешних ошибок. Ошибка доставки должна отображаться мастеру; «отправлено» не означает «прочитано».


## Когда создаются уведомления

| Вид | Получатель | Момент |
| --- | --- | --- |
| new | Назначенный исполнитель / ответственный бригады | Текущее назначение |
| reminder | Исполнитель / ответственный | За 30 минут до срока, если этот момент ещё впереди |
| unaccepted | Мастер наряда | Через 3 минуты для emergency, через 10 для остальных от текущего назначения |
| emergency_queued | Мастер наряда | Аварийный наряд осознанно поставлен в очередь |
| overdue | Исполнитель / ответственный и мастер | Строго после due_at |

ACCEPTED и QUEUED считаются принятием и отменяют эскалацию непринятия. Переназначение меняет assignment_version: старые задания больше не актуальны. У завершённого или отменённого наряда уведомления не отправляются. Перед каждой отправкой сервер повторно проверяет статус, назначение и доступ получателя. Сроки передаются в бизнес-функции явным временем для тестов.

Сообщение содержит статическую подпись причины, номер наряда, приоритет и срок; описание работ и персональные данные не передаются. Подпись различает новый наряд, напоминание, непринятие, аварийную очередь и просрочку.

Notifications и независимые receipts outbox хранятся в PostgreSQL; published_at событий Т03 остаётся доступным будущим потребителям. Worker забирает задания с lease и уникальным токеном владения: старый процесс не может подтвердить чужую повторную попытку. Блокировки БД снимаются до сетевой отправки. Уже начатая отправка может завершиться после отмены наряда или отключения привязки; действия в PWA сохраняются. Сетевой timeout ограничивает ожидание сокета, а не абсолютную длительность ответа; при неопределённом исходе lease не исключает повтор.

Внешний Telegram не поддерживает атомарную транзакцию с нашей БД: после неопределённого сетевого исхода возможен повтор сообщения.

Статусы: PENDING — ожидает срока; LEASED — взято worker; RETRY — временная ошибка; BLOCKED — нет привязки/настроек; SENT — API Telegram подтвердил отправку; FAILED — окончательная ошибка/лимит попыток; CANCELLED — задание не актуально. Отсутствие привязки или настроек видно и не расходует сетевые попытки. 403 блокировки бота — окончательная ошибка; 429 использует retry_after; временные сбои повторяются ограниченно.

## Обязательная живая проверка

После настройки бота, публичного HTTPS и Т04:

- Привязать мастера и исполнителя с двух телефонов, создать наряд и открыть уведомление в авторизованной карточке.
- Проверить новый наряд, напоминание за 30 минут, непринятие через 3 минуты для emergency и 10 минут для остальных, просрочку исполнителю и мастеру. В автоматических тестах время передаётся явно; системные часы для демо не подменяются.
- Принять/поставить в очередь, переназначить и отменить наряд: неактуальные задания не должны доставляться. Аварийная очередь отдельно видна мастеру.
- Заблокировать бота и проверить видимый отказ доставки; отключить сеть/перезапустить worker, проверить сохранённые задания и восстановление.
- Записать commit SHA, среду, реальные результаты и ограничения без токенов и личных Telegram ID.

Пока бот не создан, живая проверка имеет статус BLOCKED. Подмена внешнего API в тестах не подтверждает настоящую доставку или работу на телефонах.
