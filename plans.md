# НарядAI — план реализации и состояние проекта

> Для ИИ-агентов: выполнять назначенную задачу по Superpowers `executing-plans`, если навык доступен. `subagent-driven-development` использовать только при явно выбранной работе с подагентами. Шаги отмечаются чекбоксами; отсутствие плагинов не мешает следовать описанным контрактам и проверкам.

**Цель:** за 5 дней силами 3 участников показать работающий на телефонах цикл ремонтного наряда, ИИ-проверку и аналитику.
**Архитектура:** одна PWA, модульный FastAPI, PostgreSQL, приватные фото и отдельный worker. Telegram доставляет уведомления; решение о закрытии принимает мастер.
**Стек:** рабочая версия находится в [readme.md](readme.md#stack); менять через журнал решений ниже.
**Спецификация:** самодостаточный минимум из исходного ТЗ сохранён в разделах «Глобальные требования» и «Контракты». Вложения из чата и локальные пути автора для выполнения плана не нужны.

## На что смотреть при ревью

1. Чужой UUID в URL, фото или WebSocket: исполнитель не получает данные другого сотрудника — T02/T05.
2. Повтор запроса или одновременные переходы: одно действие не дублирует расход материалов, события или задания — T03/T06.
3. Новый отчёт поступил раньше ответа ИИ на старый: старый ответ не меняет актуальный наряд — T07.
4. Telegram заблокирован, модель недоступна, процесс перезапущен: задание сохраняется, ошибка видна, наряд не закрывается сам — T06/T07.
5. Ожидание запчастей, смена через полночь, пересечение простоев: показатели не обвиняют сотрудника автоматически и не удваивают простой — T08.

<a id="contracts"></a>
## Контракты — рабочая спецификация для параллельной разработки

Изменения этих контрактов записывать в журнал решений и отражать в зависимых задачах. Названия ниже — целевые, код ещё не создан. Общие HTTP-схемы принадлежат B; схемы результата ИИ — C; A генерирует клиентские типы из OpenAPI.

### C1. Данные, авторизация и API

- Идентификаторы — UUID; время хранится в UTC, передаётся ISO 8601 с часовым поясом; пояс предприятия настраивается, стартовое значение `Asia/Qostanay`. Количество материала — положительное decimal, единица берётся из справочника.
- `User`: id, display_name, role (`master|worker|manager|admin`), specialty, grade, brigade_id, shift_id. `Shift`: start_at, end_at; статус занятости вычисляется из смены, активного наряда и очереди. Участок доступа хранится явно.
- `WorkOrder`: id, number, work_type (`planned|emergency`), description, area_id, equipment_id, assignee_id или brigade_id (ровно одно), master_id, priority (`emergency|high|normal|planned`), due_at, status, version, assignment_version, created_at. Для бригады назначается один ответственный исполнитель, остальные видят разрешённую карточку без права конкурентного ведения статусов.
- Связанные данные: `WorkOrderEvent`, `Submission` с номером revision, `Photo`, `MaterialUsage`, `AIReview`, `MasterDecision`, `DowntimeInterval`; справочники оборудования, шифров и нормативов. Восьми сущностей исходного ТЗ недостаточно для версий отчётов и устойчивой доставки — это осознанное расширение модели.
- Вход по логину и паролю/ПИН; только хеш секрета, ограничение попыток, серверная сессия в HttpOnly cookie. Приложение и API в одном origin; изменяющие запросы проверяют CSRF. Telegram-привязка не заменяет вход и авторизацию.
- `/api/v1`: `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`; `GET /catalog/{kind}`; `GET /shift`; `GET|POST /work-orders`; `GET /work-orders/{id}`; `POST /work-orders/{id}/actions`; `POST /work-orders/{id}/submissions`; `POST /work-orders/{id}/photos`; `GET /photos/{id}`; `POST /work-orders/{id}/decision`; `GET /reports/shift`; `GET /reports/rating`; `GET /analytics/anomalies`.
- `GET /work-orders` поддерживает area_id, equipment_id, assignee_id, priority, status и пагинацию. Отчёты принимают start_at/end_at и разрешённые фильтры участка, оборудования, исполнителя/бригады; интервалы `[start_at, end_at)`.
- Для действий: `Idempotency-Key` плюс `expected_version`; первый запрос атомарно сохраняет изменение, событие и outbox. Повтор возвращает тот же результат; тот же ключ с другим телом — 409; устаревшая версия — 409. Ошибки: 401 без входа, 403 для запретного действия, 404 для недоступного чужого объекта, 422 для невалидного ввода.
- WebSocket `/api/v1/events` авторизуется сессией и отдаёт только разрешённые события: `event_id`, `type`, `work_order_id`, `version`, `occurred_at`. После переподключения клиент перечитывает актуальные данные через API; события служат сигналом обновления.
- `WorkOrderView` содержит поля WorkOrder, is_overdue и allowed_actions; подробная карточка дополнительно содержит events и текущую submission. `PhotoView`: id, work_order_id, type, received_at, read_url (защищённый маршрут API). `SubmissionView`: поля Submission, id и missing_evidence. Эти схемы определяются в указанных в T02/T05 Pydantic-модулях; фронтенд не ведёт независимые копии типов.

### C2. Жизненный цикл

На исходной схеме **10 состояний**, а не 9. Добавляется `CANCELLED` для предусмотренной текстом отмены; просрочка не является состоянием.

| Действие | Откуда → куда | Кто / условие |
| --- | --- | --- |
| create | новое → ISSUED | Мастер; обязательные поля R02 |
| accept | ISSUED или QUEUED → ACCEPTED | Назначенный исполнитель |
| queue | ISSUED или ACCEPTED → QUEUED | Исполнитель; задаётся порядок очереди |
| reject | ISSUED, ACCEPTED или QUEUED → REJECTED | Исполнитель; причина обязательна |
| reassign | ISSUED, ACCEPTED, QUEUED, REJECTED или PAUSED → ISSUED | Мастер; причина, новый ответственный и увеличение assignment_version |
| start | ACCEPTED → IN_PROGRESS | Исполнитель; не более одного активного наряда у ответственного |
| pause / resume | IN_PROGRESS → PAUSED → IN_PROGRESS | Исполнитель; причина паузы, отдельные интервалы ожидания; при resume нет другого активного наряда |
| submit | IN_PROGRESS → SUBMITTED | Исполнитель; новая неизменяемая revision отчёта |
| begin_review | SUBMITTED → AI_REVIEW | Worker; задача привязана к revision |
| request_rework | AI_REVIEW → REWORK | Проверка с обоснованным вердиктом или мастер |
| restart | REWORK → IN_PROGRESS | Исполнитель; прежние отчёты сохраняются, нет другого активного наряда |
| close | AI_REVIEW → CLOSED | Мастер; обязательные доказательства присутствуют |
| override_close | REWORK → CLOSED | Мастер; причина несогласия с ИИ обязательна, требования к полноте не обходятся |
| cancel | любое незавершённое → CANCELLED | Мастер; причина обязательна |
| reprioritize | статус сохраняется | Мастер; событие со старым и новым приоритетом |

`CLOSED` и `CANCELLED` терминальны в MVP. Выданный наряд с приоритетом emergency требует явного принятия. Входящие действия после переназначения повторно проверяют исполнителя. Старая задача ИИ не меняет отменённый или переназначенный наряд.

`is_overdue` вычисляется по due_at до исполнения и во время доработки; ожидание приёмки в SUBMITTED/AI_REVIEW учитывается отдельно. Пауза не меняет due_at автоматически. Активное время, ожидание, приёмка и простой оборудования хранятся раздельно.

### C3. Отчёт исполнителя и фотографии

- `Submission`: work_order_id, revision, work_description, fault_code_id, materials[], no_materials_used, after_photo_ids[], comment, submitted_at. Пустой список материалов допустим при явной отметке «не потребовались»; количество каждой указанной позиции больше нуля.
- Отправка без обязательного фото разрешена как **попытка проверки**, чтобы выполнить сценарий ТЗ. Сервер фиксирует `missing_evidence`, проверка возвращает REWORK, закрытие блокируется. Это не разрешение закрывать неполный наряд.
- Фото связано с нарядом, типом before/after, автором, временем получения сервером и, если есть, заявленным временем съёмки. Проверять фактический MIME, размер и доступ; имена путей не принимать от клиента. Целевой размер сжатого фото 300–500 КБ, предел после загрузки 5 МБ; сравнение качества проводится на демотелефонах.
- Хеш совпадающего файла и perceptual hash дают сигнал повторного использования; EXIF не является доказательством свежести. Для внешнего ИИ готовится разрешённая копия без персональных данных. Отсутствие фото до означает «сравнение невозможно», а не автоматический отрицательный вердикт.

### C4. Telegram и фоновые задачи

- `POST /telegram/link-token` доступен вошедшему пользователю: криптографически случайный одноразовый токен, срок 10 минут; в БД хранится хеш. `/start <token>` связывает сотрудника с числовым telegram_user_id и private_chat_id; повторное использование/просрочка отклоняются.
- `POST /telegram/webhook` проверяет секрет webhook. В Telegram только номер, приоритет, срок и HTTPS-кнопка «Открыть наряд»; для деталей требуется сессия PWA. Никаких изменений статуса через простую ссылку GET.
- `Notification`: kind, work_order_id, assignment_version, recipient_id, due_at, dedup_key, attempts, status. Напоминание за 30 минут создаётся, только если этот момент ещё не прошёл; просрочка — после due_at; непринятие — через 3/10 минут от текущего назначения. Принятием считается ACCEPTED или осознанная постановка QUEUED; аварийный наряд в QUEUED отдельно виден мастеру.
- Ключ дедупликации включает наряд, назначение, получателя и вид уведомления. Повторные доставки webhook также дедуплицируются по update_id. Перед отправкой повторно проверяются актуальность статуса и назначения.
- Jobs/outbox хранятся в PostgreSQL; worker забирает задачу атомарно с lease, подтверждает результат и восстанавливает просроченный lease после сбоя. Для временных ошибок ограниченные повторы с увеличением задержки; 429 учитывает retry_after, 403 блокировки бота становится видимой ошибкой доставки.
- Дедупликация собственных событий обязательна; абсолютную exactly-once доставку во внешний Telegram при сетевом таймауте не обещать. Отправлено не означает прочитано. Требование 3 минут относится к реакции/эскалации сервера, а не гарантии звукового уведомления на телефоне.

### C5. Проверка ИИ и приёмка

- Правила полноты и расчёты выполняются кодом; LLM получает обезличенную заявку, работы, допустимые фото, нормы и уже вычисленные показатели. Текст отчёта/изображения не может менять системные инструкции или давать модели полномочия.
- `ReviewInput`: work_order_id, submission_revision, assignment_version, problem, work_description, material_checks, timing_checks, photo_refs, checklist. `ReviewResult`: verdict (`accepted|accepted_with_notes|requires_rework|human_review`), score (1–5 либо null при недостатке данных), findings[] (`code`, `severity`, `message`, `evidence_refs[]`), missing_evidence[], limitations[]. Каждый evidence_ref существует во входных данных.
- Применяется строгая JSON-схема. Отказ модели, таймаут, ошибка схемы или недостаточное качество фото дают `human_review` с объяснением; это не отрицательная оценка исполнителя. «Уверенность» модели не трактуется как измеренная вероятность правильности.
- Результат хранит model_id, prompt_version, submission_revision, время и usage/latency, если доступны. Повторная обработка одной revision не создаёт вторую оценку; устаревшая revision не меняет текущий статус.
- `accepted` и `accepted_with_notes` оставляют наряд в AI_REVIEW до решения мастера; `requires_rework` возвращает REWORK. Мастер может изменить оценку с обязательным объяснением; автоматического CLOSED нет.
- Для демо: два утверждённых шаблона доказательств, например видимая течь и загрязнение/отсутствующий элемент. ИИ проверяет соответствие шаблону; исправность скрытых узлов и безопасность запуска по одному фото не удостоверяются.

### C6. Аналитика и рейтинг

- Отчёт смены: выданные, исполненные, закрытые, просроченные и отклонённые наряды, загрузка, простой и текстовая сводка. Эти счётчики не смешиваются; времена границ смены берутся из Shift, а не календарной даты.
- Простой считается по `DowntimeInterval` оборудования как объединение пересекающихся интервалов; длительность нарядов не суммируется как простой. Повтор — совпадение equipment_id и fault_code_id в 7 дней; это сигнал для проверки причины.
- Рабочая формула рейтинга: `100 × (0.50Q + 0.25T + 0.15R + 0.10V)`, компоненты 0..1. Q — средняя окончательная оценка мастера / 5; T — доля сдач в согласованный срок с отдельно показанными подтверждёнными внешними задержками; R — доля без подтверждённого возврата/повтора по причине качества; V — min(1, сумма нормативных часов закрытых работ / доступные часы смены). Формула предварительная и меняется через D06.
- Для R ждать завершения семидневного окна наблюдения; неполные окна не считать успешными. Подтверждённые внешние задержки могут менять оценочный срок для T, но не исходный due_at и историю просрочек. Обоснованность отказа определяет мастер; необоснованные отказы отображаются отдельным счётчиком, без скрытого штрафа.
- При недостатке данных компонента помечается «нет данных», веса доступных компонент нормируются; без закрытых работ итог не считается. Показать размер выборки и сравнивать работников сопоставимой специальности/типа работ. Для периода из нескольких смен суммируются нормативные и доступные часы.
- Закономерности: повтор одного шифра на одном оборудовании; поломки вскоре после ППР; расход материала выше сопоставимой нормы. Каждый результат содержит числа, период и id нарядов. При отсутствии нормы не утверждать завышение; связь со сменой/исполнителем не объявлять причиной.
- В LLM передаются агрегаты и ссылки на факты для формулировки сводки. Расчёт чисел и сортировка выполняются SQL/Python; весь журнал из 500 записей не пересылается модели в каждом запросе.

## Обновление прогресса и передача работы

1. Перед началом: сверить текущую ветку и план, выбрать задачу с выполненными зависимостями, записать владельца и ветку вида `feat/T03-work-order-lifecycle`.
2. Работа выполняется в своей ветке; интерфейсы обсуждаются до несовместимого изменения. Не перезаписывать одновременно весь `plans.md`: менять свою строку и собственную передачу работы, при интеграции сохранять актуальные записи коллег.
3. До интеграции использовать REVIEW, после проверки и включения в основную ветку — DONE. Одно доказательство успеха записывается один раз; не копировать длинные логи в начало плана.
4. При блокировке записать конкретную зависимость и доступный следующий шаг. Независимые задачи продолжаются; отсутствие ключа ИИ не блокирует интерфейс или переходы статусов.
5. После сессии обновить текущую сводку, если изменился этап/следующая задача, и оставить короткую запись ниже. Старые подробности доступны в Git; не наращивать бесконечный журнал в контексте каждого агента.

Шаблон передачи для каждой активной задачи:

```text
Задача: Txx | статус: IN_PROGRESS / REVIEW / BLOCKED
Владелец и ветка:
Что фактически сделано: 1–3 пункта, ссылки на файлы/PR
Проверка: команда, среда, PASS/FAIL/НЕ ЗАПУСКАЛАСЬ, commit SHA
Что осталось / блокер:
Следующее конкретное действие:
Изменённые контракты / решения: Cx / Dx либо «нет»
```

**Активные передачи:** нет; первой взять T01.
